# 上下文与常见模型

[返回本章大纲](../04_AI与Agent的工作方式.md) · [上一节：语言模型](05_从文本向量到语言模型.md) · [下一节：Agent Harness](07_文本命令与Agent_Harness.md)

本节对照原文续写和聊天，并通过真实请求说明历史记录、文件和上下文的关系。

## 一、原文续写与聊天输入

输入“姚明是”后，原文续写会接着补全文本，聊天模式则生成一条助手回复。

**原文续写**：把这一段文本作为前缀，接着生成。

```text
姚明是▌
```

**聊天**：把用户消息放入对话格式，在助手的位置生成回复。

```text
〈用户开始〉
姚明是
〈用户结束〉
〈助手开始〉
▌
```

上述中文标记用于展示消息结构，具体模型使用相应的控制 token。聊天模式依据角色消息组织输入，原文续写模式依据文本前缀组织输入。

同一模型可以通过不同接口接收两种输入；输入格式会影响生成结果。

在网页聊天界面输入“姚明是”，再用 `inspect_llm.py next --text '姚明是'` 查看原文续写的下一个 token。两次请求的输入格式和输出长度设置不同。

## 二、聊天模板与系统提示词各自的作用

**聊天模板**将“谁说了什么”的消息列表，转换成模型期望的文本序列。**系统提示词**是其中一种可能的消息内容，用于提供行为要求；聊天格式还包含角色标记与消息边界。

常见角色包括：

| 角色 | 含义 |
| --- | --- |
| user | 用户提出的问题或提供的资料 |
| assistant | 之前的助手回答，以及接下来要生成回答的位置 |
| system | 系统提供的行为要求，是否存在取决于具体服务和配置 |
| tool | 工具实际执行后返回的信息，后续小节展开 |

角色格式由具体模型和服务决定，上表只展示这一类角色格式，具体协议请查看所用服务文档。

本地演示入口删除请求中的 system 消息，保留用户和助手的角色分隔。聊天训练形成的行为仍体现在模型参数中。

本地演示只生成文本。真实文件操作需要工具调用记录和文件结果作为证据。

## 三、上下文的组成

**上下文**是模型本次计算实际收到的信息，包括当前问题、提供的资料、选入的历史对话和工具结果。

长期训练得到的规律主要体现在模型参数中。

| 情况 | 进入本次输入的条件 |
| --- | --- |
| 文件保存在电脑某个目录 | 程序先读取文件，再将正文加入请求 |
| 用户粘贴了一段记录 | 如果实际提交给模型，就进入输入 |
| 上次对话的内容 | 本次请求带上相应历史或摘要时可使用 |
| 程序读取文件后提交正文 | 提交的正文可以成为上下文 |
| 工具执行了计算 | 还需要把执行结果交回模型，才能用于后续回答 |

核对模型依据时，需要查看实际请求中包含的信息。

## 四、历史对话的传递

外围程序保存对话，并在后续请求中提交相关历史消息。

例如第二次提问时，可以提交：

```json
{
  "messages": [
    {"role": "user", "content": "样品编号是 Z-731。"},
    {"role": "assistant", "content": "收到记录。"},
    {"role": "user", "content": "样品编号是什么？请只回答编号。"}
  ]
}
```

上例把编号记录和当前问题一起提交，模型可以使用编号作答。

不同产品通过用户端历史列表、服务端会话、摘要或检索提供历史信息。

缓存加速重复前缀的处理；会话管理机制负责提供跨请求历史。

## 五、真实演示：同一个模型，改变提供的信息

运行[上下文对照脚本](../../演示/本地语言模型/context_demo.py)：

```bash
python3 context_demo.py
```

在脚本目录运行命令，连接已启动的 WSL 本地服务。[教学样品记录](../../演示/本地语言模型/教学样品记录.txt)包含虚构编号“Z-731”。

脚本依次提交五组独立请求，保持模型与生成设置一致，改变消息列表：

| 场景 | 这次提供什么 | 本机一次实际输出 |
| --- | --- | --- |
| 仅提问 | 只有编号问题 | `编号` |
| 带上历史记录 | 编号记录、示意的助手确认、当前问题 | `Z-731` |
| 丢掉历史只发末句 | 再次只提供问题 | `编号` |
| 只提供文件名 | 请读取某个文件，请求中仅有文件名信息 | `编号：2023-04-01` |
| 实际读文件后提供正文 | 脚本读取文件，明确将内容放进用户消息 | `Z-731` |

这是 Qwen3-0.6B Q8_0 的一次真实运行，temperature=0.7、seed=42。见[完整请求、模板和实测输出](../../演示/本地语言模型/上下文实测.json)。这组结果对应上述模型与设置；换模型或重复运行时需记录各自输出。

第二种场景中的“收到记录。”是脚本预写的历史消息；最终答案由模型生成。

### 结果与请求内容

- 第二、五种请求提供了编号；第一、三、四种提供了问题或文件名。
- 第四种请求提供文件名，模型生成的日期样式编号缺少文件内容依据。
- 第五种请求由 Python 读取文本，再把正文发送给模型。
- 核对回答时，同时查看模型实际收到的记录。

### 输入变化与输出结果

初次尝试使用较长记录和另一种问题措辞，小模型在五种场景中均给出保守答复。[初次运行记录](../../演示/本地语言模型/上下文实测_初次失败.json)保留了回答原文。

简化记录与问题后，脚本得到上表结果。两次尝试同时改变了记录和问题措辞。分析各因素的影响，需要分别控制输入变量。

## 六、上下文长度与输入选择

**上下文窗口**表示模型或服务一次能够处理的 token 范围，具体限制与模型、实现和配置有关。输入、历史、模板及输出通常共同占用相应预算，实际还要看服务如何管理。

本课 WSL 演示明确配置为 2,048 token 上下文、单并发。这个值是本次运行设置，与模型卡标示的最大能力各有含义；token 数量与汉字数量也采用不同计量方式。

超过预算时，服务可能拒绝请求、截断内容、移动窗口或进行其他处理，保留哪些信息由服务和应用的处理策略决定。应用可能先做摘要或检索，再挑相关内容送入模型。

长度仍在预算内时，过多信息、相互冲突或对应关系模糊也会影响回答。有效依据来自相关、清楚、可核查的信息。

对照报告中的 `formatted_prompt_tokens` 显示各场景输入长度。报告也保留了服务器返回的 usage。

## 七、文献任务的输入材料

假设希望模型汇总论文中的某个测试结果，可以先准备：

1. 明确任务：提取哪个样品、哪种测试和哪些字段。
2. 提供相关原文、表格或已读入的解析结果，并保留来源位置。
3. 说明输出要求：例如单位、表格列名，以及缺失信息如何标记。
4. 检查生成结果是否与原文一致，是否混淆不同样品或条件。

上传 PDF 之后，工具可能只提取文字，也可能处理图像、表格或部分页面，具体取决于产品。应核对工具实际提取的内容，特别检查图表、公式与扫描页。

这里聚焦输入来源，PDF 解析工具和文献任务留作后续学习。
